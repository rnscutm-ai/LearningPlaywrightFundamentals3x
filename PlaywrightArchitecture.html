ARCHITECTURE NOTES · BROWSER AUTOMATION

What happens backstage when Playwright runs a test

A test script never touches the browser directly. It hands its lines to a server, which hands them to the browser, which performs the scene. This is a tour of that whole chain — client, protocol, server, and the three browser engines underneath.

01 — THE CENTRAL DECISION

One server directs three different actors

Playwright's core design choice is to separate the code you write from the browser that runs it, and to put a single coordinating process — the Playwright Server — in between.

Your test calls something like page.click(). That call doesn't reach into the browser. It's serialized into a message and sent over a long-lived WebSocket to a Node.js server process. The server is the only thing that ever speaks to a browser directly, using each engine's own remote-control protocol. It translates your one command into whatever that engine needs, waits for the result, and streams the answer back.

Because the connection is a persistent, full-duplex socket rather than a request-and-wait HTTP call, the server can also push things at your test unprompted — a console message, a new tab opening, a network request firing — instead of only replying when asked.

Client, server, and browser are three separate processes. The server is the only one that speaks a browser's native protocol — Chrome DevTools Protocol for Chromium, and CDP-shaped protocol layers that the Playwright team patches directly into Firefox and WebKit's own source, since neither ships an equivalent by default.

02 — INSIDE THE SERVER

Five layers between your call and the click

The client-server split isn't just two boxes — the source is organized into a stack, each layer responsible for one translation step.

01

Client API

The public methods you call — page.click(), locator.fill(). Every client object (Page, Frame, BrowserContext) inherits from a base class that turns a method call into an outgoing message instead of doing the work itself.

ChannelOwner
02

Protocol definition

A schema file describes every method, its parameters, and the events it can emit. Client and server code for these messages is generated from this single definition, so the two sides can never quietly drift apart.

protocol.yml
03

Dispatcher

On the server, a dispatcher exists for every object type — BrowserDispatcher, PageDispatcher, FrameDispatcher, and so on. It receives a protocol message and routes it to the matching internal object, then reverses the trip for the response.

server-side routing
04

Server / core

The actual automation logic: computing whether an element is actionable, managing contexts and frames, recording network traffic, driving input events. This layer knows nothing about WebSockets — it only knows browsers.

browser-agnostic
05

Browser-specific driver

The thin bottom layer that actually speaks CDP, or the patched equivalent that Firefox and WebKit expose. This is the only part of the stack that changes per browser engine.

CDP / patched protocols
Why bother with a generated schema at all? It gives Playwright a hard boundary between "the API developers write against" and "how a browser is actually automated." That boundary is also what lets one Node.js server support Python, Java, .NET, and Go clients — each language ships a small binding plus a bundled copy of the Node runtime, and talks to it over stdio instead of reimplementing the automation logic per language.
03 — ISOLATION

Contexts, not new browsers

Launching a browser process is slow and heavy. Playwright's answer is to launch one browser and carve it into cheap, disposable sessions instead.

A browser context is roughly equivalent to a fresh incognito profile — its own cookies, local storage, permissions, and cache — created inside an already-running browser process in milliseconds. A page is a single tab within that context. Because contexts don't share state, dozens of them can exist side by side inside one browser, which is what makes running many tests in parallel practical: each test gets a clean slate without the cost of a brand-new browser launch.

One browser process

Chromium, Firefox, or WebKit starts once and stays warm. Starting it is the expensive part, so Playwright avoids repeating it.

Many contexts inside it

Each context is an isolated session — its own storage and cookies — created and torn down cheaply, which is what a fresh test run actually needs.

04 — TIMING

Actions wait for the page to mean it

Before performing an action like a click or a fill, Playwright doesn't just check that an element exists in the DOM — it runs a small set of actionability checks and keeps re-checking them until they all pass or a timeout is hit. This is what removes the sleep-based waiting that made older automation tools flaky.

check

Is it attached to the DOM and visible?

check

Is it stable — not mid-animation or mid-transition?

check

Does it receive events, or is something else covering it?

check

Is it enabled, and not read-only where that matters?

retry

If any check fails, wait briefly and run the whole set again.

The same retry idea extends to assertions — a web-first assertion like expecting some text to appear doesn't just check once, it polls until the condition holds or the timeout expires. The trade-off: actionability is judged against a page that keeps changing, so an element that re-renders mid-check can still cause a failure. The usual fix is anchoring a locator to something stable rather than to text that gets swapped out.
05 — THE TEST RUNNER

Workers, fixtures, and a dependency graph

Playwright the automation library and Playwright Test the runner are separate layers. The runner is what most people write tests against day to day, and it adds its own architecture on top of everything above.

A worker is a full OS process, not a thread — the runner spawns several of them (by default, roughly half the machine's logical cores) and hands each one a batch of test files to get through on its own. Workers share nothing: no variables, no browser, no cookies. When a test fails, its worker is discarded and a fresh one takes its place, so one bad test can't contaminate the next.

Fixtures are the runner's dependency-injection system — the mechanism that hands a test its browser, page, or logged-in session, and cleans each one up afterward. A fixture can be scoped to a single test or to an entire worker, and the runner resolves the whole dependency graph before a test body ever runs.

ConceptScopeWhat it isolates
WorkerOS processIts own browser instance, memory, and environment — never shared across workers
Test fixtureOne testTorn down and rebuilt fresh for every single test, e.g. a new page
Worker fixtureOne workerReused across every test that worker runs, e.g. a launched browser
ShardOne machineA whole slice of the suite, split across separate CI runners rather than processes

Workers scale parallelism on one machine; sharding scales it across several machines once one machine's CPU is the bottleneck. Tuning generally starts with workers and only reaches for sharding after that.

06 — LOOKING BACK

A trace is a recording of the whole chain

Because every action already passes through one central server, that server is well-placed to record everything going through it. Turning tracing on captures a timeline of actions, DOM snapshots before and after each step, network activity, and console output, and packages it into a single file that the Trace Viewer can replay later — without needing to run the test again to see what happened.

07 — WHERE IT'S HEADED

The same server, a newer kind of client

The client-server split has stayed essentially the same since Playwright's first stable release; what's changed around it is the tooling. The most recent addition is an MCP server that exposes Playwright's actions as structured tools an AI agent can call directly — the same underlying server, but with an AI system sitting in the client seat instead of a fixed test script.
